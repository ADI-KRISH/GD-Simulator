READ THIS FIRST
-------------------------------------------------------------------------------
In normal development there are only TWO ports you touch:

    8000    backend    the gateway - all 19 module routers mounted
    5173    frontend   the shell   - every built module UI mounted

The gateway (Backend/gateway) mounts all 19 module routers into one API, and
the shell (Frontend/shell) mounts all built module UIs into one web app. A
student never hops between ports.

But every module ALSO runs standalone on its own reserved port, for focused
development and debugging:

    cd GD_Arena  && .venv\Scripts\python -m uvicorn services.main:app --port 8114
    cd frontend  && npm start                                          (:5214)

    or simply:   start_gd.bat             this module, API and web, no Docker
                 start.bat                with its own containers (see below)

  GD Arena is a Next.js app with its own backend, so the shell frames it at
  /gd rather than mounting it from source.

Both put every service in ONE Windows Terminal window, one tab each, with the
control tab last. Ports live in scripts\services.txt - which reads them from
here, so this file stays the single source of truth.

Same routers, same components either way - the standalone entrypoint only adds
the providers the gateway/shell would otherwise own. What you fix in isolation
is what students get.

Never hardcode a port in application code. Read it from env:
    backend    BACKEND_PORT     (default 8000)
    frontend   VITE_API_BASE    (default http://127.0.0.1:8000)

A MODULE'S OWN CONTAINERS
-------------------------------------------------------------------------------
A module that brings its own infrastructure (docker compose) binds it to
127.0.0.1 on host ports recorded here - never the spine's 5432 / 6379 / 9000,
and never another module's. Take a new one here, then tick it off.

  M14   GD Arena - GD_Arena/infra/docker-compose.yml (start.bat; human rooms)
          5442   PostgreSQL           GD's own database (the spine is 5432)
          6389   Redis                cache + its Streams event bus
          7880   LiveKit              signalling, WebSocket + HTTP (the SFU)
          7881   LiveKit RTC/TCP
          7882   LiveKit RTC/UDP      one UDP port, not a range
          9010   MinIO S3 API         recordings
          9011   MinIO console
          9090   Prometheus           scrapes GD's API on 8114
          8314   Grafana              an ops app - see 83xx
        GD's no-Docker mode (start_gd.bat, the platform's) needs none of these.


DO NOT USE — known conflicts on Windows dev machines
-------------------------------------------------------------------------------
  3000   claimed by too many JS tools; Langfuse moved to 3001 for this reason
  5000   Windows "System" / SSDP on some builds; also macOS AirPlay
  7000   macOS AirPlay Receiver
  8080   default for a dozen Java/Tomcat/proxy tools
  27017  MongoDB — we do not use Mongo; if this is listening, something else is


CHECKING A PORT
-------------------------------------------------------------------------------
  PowerShell    Get-NetTCPConnection -LocalPort 8000 -State Listen
  cmd           netstat -ano | findstr :8000
  kill by pid   taskkill /PID <pid> /T /F

The launchers shut services down by PID, recorded per service in .run\<id>.pid.
If a port is stuck after a crash, find the PID with the commands above rather
than killing by window title — on Windows 11 the window title belongs to the
terminal host, not to your service, so a title-matched taskkill can close the
whole terminal including the control tab.
